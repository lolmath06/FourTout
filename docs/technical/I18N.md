# Internationalization

[← Documentation](../README.md)

## Summary

- The application bundles 16 languages. Translation never requires an online
  service or a download.
- Interface source text is written **in French in the code**, for example
  `t("Fichier illisible.")`. Translations use a stable hash of that text.
- Tools are **never duplicated by language**. Each `ToolDefinition` remains
  unique; localized text lives separately and is indexed by tool ID.
- Fallback order is **displayed language → English → source text**. A raw key
  is never displayed. All shipped catalogs are complete, so fallback is a
  safety net rather than the normal path.
- No third-party i18n dependency is used. `src/i18n/` implements the supported
  ICU subset, and formatting uses `Intl`.

`pnpm i18n:status` reports real coverage for every locale. All 16 real locales
must remain at 100%. `System` is a preference, not a translation locale.

## File layout

```text
src/i18n/
  locales.ts          locales and system-language matching
  format.ts           reduced ICU format and message hashing
  runtime.ts          active locale, loading, t(), tx(), msg(), localized()
  Trans.tsx           tagged messages (<0>…</0>) rendered as React
  intl.ts             numbers, dates, relative time, sizes, sorting
  native.ts           recognition of messages originating in Rust
  native.json         templates extracted from Rust code (generated)
  messages/
    fr.json           source catalog: hash → source text (generated)
    en.json …         one translated interface catalog per locale
  catalog/
    en.json …         localized tool and category metadata
scripts/i18n/
  extract.mjs         regenerates fr.json and native.json from the code
  status.mjs          reports coverage and stale catalog entries
```

English is loaded at startup because it is the safety fallback. Other locales
are separate modules parsed on demand by `loadLocale()`.

## Writing a message

```tsx
import { t, msg, tx, localized, Trans } from "@/i18n";

t("Fichier illisible.");
t("Page {page}", { page: 3 });
t("{count} {count, plural, one {fichier} other {fichiers}}", { count });
<Trans source="Écrit dans <0>{output}</0>" values={{ output }} components={[<code />]} />;
```

- **Variables** such as `{name}` are inserted as supplied. A port number like
  `8080` or a year does not gain a thousands separator.
- **Plurals** use
  `{n, plural, =0 {…} one {…} few {…} many {…} other {…}}`.
  `Intl.PluralRules` selects the displayed locale's branch, and `#` becomes a
  **formatted** number. A translation may introduce a plural absent from the
  source; Polish and Russian often need this.
- **Numbered tags** such as `<0>…</0>` and `<1/>` are rendered by `<Trans>`, so
  a sentence containing emphasis or a link remains a single translatable unit.
- For **module-level constants** such as option lists, use
  `const LABELS = localized(() => ({ … t("…") … }))`. It is reevaluated after
  each language change without changing its consumers.
- `msg("…")` marks text that will be translated at render time. `tx(value)`
  translates a value that may be a known source message or native message, and
  otherwise treats it as data and returns it unchanged.

Changing the language remounts the React routing tree through its locale key.
Everything updates immediately without restarting, while the current URL and
open tool are preserved.

## Tool catalog

`ToolDefinition` under `src/core/tools/catalog/` retains source text and all
structural metadata. Translations live in `src/i18n/catalog/<code>.json`:

```json
{
  "categories": { "pdf": { "name": "PDF", "description": "…", "keywords": ["…"] } },
  "tools": {
    "pdf-compress": {
      "name": "Compress a PDF",
      "description": "…",
      "keywords": ["compress", "shrink", "…"],
      "aliases": ["compress pdf", "…"],
      "note": "…"
    }
  }
}
```

The interface never reads `tool.name` directly. It uses helpers in
`core/tools/localized.ts`, including `toolName`, `toolDescription`, `toolNote`,
and `categoryName`. Fallback works per field. IDs, routes, favorites, and recent
items never depend on language.

Keywords are written **naturally in each locale** as users would type them,
for example “pdf komprimieren” or “压缩”; they are not literal translations.
Format names remain unchanged.

## Native-layer messages

Rust errors and states arrive as already formatted French text. Rather than
rewriting the native layer, `scripts/i18n/native.mjs` extracts those strings as
**templates**, for example `Lecture impossible : {p0}`. It writes them to
`native.json` and includes them in the source catalog. At display time, `tx()`
matches a template and translates both the message and up to two nested levels
of values. Text that matches no template is displayed unchanged.

## Display locale, fallback, and persistence

- The `language` preference is stored by the existing `useSettings` local
  store. Its default is `"system"`; otherwise it holds a locale code.
- **System** selects the first supported entry in `navigator.languages`.
  Matching includes `fr-CA → fr`, `de-CH → de`,
  `zh-SG`/`zh-Hans → zh-CN`, `zh-HK`/`zh-MO`/`zh-Hant → zh-TW`,
  `pt-PT → pt-BR` as the closest available variant, and `in → id`; otherwise
  it chooses English.
- In System mode, the application listens for `languagechange`.
- `initLanguage()` in `main.tsx` applies the locale **before the first render**,
  preventing a visible language flash.
- `<html lang>` and `<html dir>` always follow the displayed locale.

## Numbers, dates, and sizes

`src/i18n/intl.ts` provides `formatNumber`, `formatDecimal`, `formatPercent`,
`formatDate`, `formatDateTime`, `formatRelativeTime`, `compareText` through
`Intl.Collator`, and `formatBinarySize` / `formatDecimalSize`. French uses
`o`, `Kio`, and `Mio`; other locales use `B`, `KiB`, and `MiB`.

**Language** and **unit system** are independent. Displaying English does not
turn kilometers into miles. Unit converters retain their own choices.

## Multilingual search

`src/core/tools/search.ts` builds and caches one index per locale:

- displayed-locale text receives full weight;
- English and French source text receives lower weight, so an English query
  can still find a tool while Japanese is displayed without outranking a
  Japanese match;
- Unicode normalization handles case and Latin accents; Chinese, Japanese,
  and Korean are segmented across script changes (`pdf を圧縮` becomes `pdf`,
  `を`, `圧縮`); stop words and directional words for all locales live in
  `src/core/tools/searchLanguages.ts`;
- ranking is deterministic, with ties resolved by `Intl.Collator`.

## Adding or changing a message

1. Write the French source text in code through `t()`, `msg()`, or `<Trans>`.
2. Run `pnpm i18n:extract` to regenerate `messages/fr.json` and `native.json`.
3. Add a natural translation for every new key to all 16 real locale catalogs.
   Preserve variables, tags, plural selectors, technical tokens, and user data.
4. Run `pnpm i18n:status`; every locale must show 100%, with no unknown key.

Changing source text changes its hash. The old translation becomes unknown and
must be moved to the new key; the test reports both conditions.

## Adding a locale

1. Declare it in `LOCALES` in `src/i18n/locales.ts`, with its native name,
   `Intl` code, and writing direction.
2. Create `src/i18n/messages/<code>.json` and
   `src/i18n/catalog/<code>.json`, both complete.
3. Add its stop and directional words to `searchLanguages.ts`.
4. Add it to `EXPECTED_LOCALES` in `src/i18n/i18n.test.ts` and add a natural
   search query in that locale.

## Tests

`src/i18n/i18n.test.ts` checks the files that are actually bundled:

- all 16 locales are declared, load, and update `<html>`;
- the source catalog matches the code and has no hash collision;
- **every locale contains 100% of source messages and no unknown key**;
- translations are well formed and preserve variables, tags, and all required
  plural categories;
- all 196 tools and 12 categories have localized names, descriptions,
  keywords, and optional notes, while IDs and routes stay unchanged;
- fallback is locale → English → source, never a raw key;
- the preference persists and updates immediately;
- System matching behaves as specified;
- natural search queries work in English, Spanish, German, Russian, Japanese,
  Korean, both Chinese variants, and every other locale; format names and
  cross-language English queries work; ranking is deterministic.

`src/i18n/runtimeStrings.test.tsx` is the runtime audit. It wraps each
translated message in pseudo-locale markers, renders all pages and all 196
tools, and fails when visible text bypasses translation.

## Auditing hard-coded strings

The audit combines static extraction by `scripts/i18n/messages.mjs` (including
warnings for non-literal calls during `pnpm i18n:extract`) and the pseudo-locale
runtime render. Legitimate exceptions are:

- proper names and brands: FourTout, FFmpeg, Piper, whisper.cpp, Tauri, and
  third-party product names;
- technical standards: format and algorithm names such as PDF, PNG, SHA-256,
  AES-256, and UTF-16 LE; SI units; keyboard names such as `Ctrl` and `Esc`;
- language names in the selector, each written in its own language;
- user data, including filenames, content, and read metadata;
- sample data inserted by developer-tool Example buttons, such as JSON or an
  encoded URL, because it is data rather than interface copy;
- standardized technical output, such as `sha256sum` manifests and the stable
  backup format's `donnees` folder and `manifeste.json`.

## Known limitations

- Native messages are recognized by extracted templates. Rust text assembled
  dynamically in an unanticipated way remains unchanged.
- Repository screenshots are language-specific. The French README uses the
  French demo; the English and other localized READMEs use the English demo.
- Public repository documentation is canonical in English and mirrored in
  full under `docs/fr/`. Root contributor and roadmap documents follow the
  same English/French pairing.
